# T6：未完成会议自动补齐

> 状态分类、退避和标记文案已由 [T7](backfill-t7.md) 修正；以下保留 T6 历史记录。

每轮同步（包括 quick、full 和列表请求失败的轮次）从本地不完整记录中，按创建时间倒序选择最多 3 条到期记录。补齐独立于水位线与历史窗口，和正常列表去重后复用详情拉取、入库和原有增强入队流程。已有不完整记录只能通过该队列进入详情阶段，避免列表扫描、全盘同步绕过上限或退避。OAuth 续期失败时停止继续发出后续批次。

HTTP 成功但内容仍不完整也算一次未补齐，状态记为 `bad_response`，保留实际返回内容并退避；只有两个完整标志都为真且入库成功才清除队列状态，增加 `updated` 和 note 中的 `backfilled=N`。新入库但仍不完整的记录从首次获取起等待 10 分钟，不在同一轮重复请求。

`backfill_state` 保存累计尝试次数、最近/下次尝试时间、安全分类和可空 HTTP 状态码。失败第 1、2、3、4 次分别等待 10 分钟、1 小时、6 小时、24 小时；第 5 次及以后保持每日重试。时间比较使用 SQLite `julianday`，兼容不同时区偏移。成功删除状态，不形成永久死队列。

## 早停取舍

同步开始时一次查询本地已完整的 ID 集合，传给 `McpMinutesSource.sync_range(..., complete_ids=...)`。确认已遍历页及当前整页时间降序后，遇到水位线前且在集合里的记录才早停；本地缺失或不完整的旧条目继续返回和翻页，同步层允许它们越过时间筛选。未提供完整集合时关闭早停；检测到逆序后继续扫描，保持已有乱序保护。

代价是每轮读取一次完整 ID，内存 O(本地完整记录数)，每条成员判断 O(1)，不逐条查询数据库。上游若有连续缺失或不完整旧条目，会多翻页；详情请求仍受已有不完整记录的 3 条队列限额约束。本地已知的不完整记录即使位于早停点之后，也由独立队列覆盖。

## 限流与诊断

详情并发默认 2，每波最多提交 2 条。连续两个详情最终失败状态为 429 后，剩余详情串行。每条录音最多请求 3 次：429 等待 30/60 秒，5xx 或超时等待 2/6 秒，其他异常不重试。MCP 详情 RPC 将重试交回录音层，避免嵌套成 9 次；OAuth 续期和非详情工具流程保留既有行为。

`sync_runs.note`、`sync_runs.http_status` 为幂等增列。状态汇总以每条最终失败录音为单位，列表阶段失败也计入；已重试成功的记录不计失败。按数字升序输出，例如 `429×16,500×2`，无状态码不伪造数字，无失败时为空。正文与凭据不会写入诊断。首页、设置同步结果、即时同步反馈及手机失败详情展示数字汇总。

列表及搜索显示「转写待补齐」，详情显示票面要求的说明。实际重试还受每轮 3 条及上述退避影响；页面文案中的 10 分钟对应首次重试间隔。
